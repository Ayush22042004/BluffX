# v0.3.0 — Final release audit, 2026-11-15

Local qualification completed. Production frontend and backend were subsequently verified on 2026-11-15 at revision `4139f1f0f91b467909a2d572d1605f3e3be70084`; see [deployment recovery and the fresh-database CI correction](v0.3.0-deployment-recovery.md). This record is not a claim that every browser, physical microphone or hosting failure has been tested.

## Changes during the final audit

- Replaced the floating fullscreen reminder with a compact banner above the header. It still returns on refresh and dismisses automatically or manually, but no longer covers room settings. The desktop utility rail accounts for the banner height.
- Added browser assertions that the reminder and utility rail do not overlap the header, and that the responsive UI audit encounters no uncaught browser errors.
- Corrected frontend revision detection to prefer Vercel's `VERCEL_GIT_COMMIT_SHA`. The same revision now supplies both the visible build identifier and `version.json`. See [Vercel's system variable reference](https://vercel.com/docs/environment-variables/system-environment-variables#vercel_git_commit_sha).
- Added optional `DEPLOYMENT_EXPECTED_REVISION` to the read-only deployment check so a shared package version cannot conceal mismatched client/server revisions.
- Allowed the ignored isolated-test configuration to carry its expected hostname. The old temporary Neon branch had expired and returned authentication failures; a fresh temporary branch restored real PostgreSQL verification without pointing tests at production.
- Updated deployment instructions for the configured Gmail HTTPS sender. Prepared an ignored, private Render environment handoff containing the required stable rate-identity secret and explicit production Gmail refresh token. No credentials were committed or printed.

The release also includes the accumulated, separately documented theme palettes, table settings, speaking indicators, natural headphone capture, mail providers, security headers and reporter contact details. Existing cards, authentication and multiplayer rules were preserved.

## Performance samples

These are local synthetic measurements, not a Render capacity guarantee. Limits were disabled only for loopback load generation; correctness/rate-limit tests ran separately.

- [20-room local report](../performance/final-audit-2026-11-15-local.json): 360 actions, 120 rounds, 90.97 ms action p95, 609 ms workload CPU, 118.7 MB peak RSS, 28.0 MB heap. This recorded sample ran alongside other release checks. A preceding unrecorded run measured 31.5 ms p95; do not compare these as an optimization claim.
- [Three-room isolated Neon report](../performance/final-audit-2026-11-15-neon.json): 18 actions, six rounds, 1930.8 ms action p95, 1926.9 ms persistence p95, 125 ms workload CPU, 79.9 MB peak RSS. There were 54 workload SQL queries, 18 commits and 48 delivered messages.
- Both two-second idle windows produced zero writes, receipt lookups or messages; the Neon run also recorded zero idle queries.
- Geographic database/network latency remains significant. Measure the deployed service before changing regions or weakening durability. No paid services or fake keep-alives were added.

## Release handoff

1. Push the verified `release/v0.3.0` branch. Keep the older production frontend until the backend is ready.
2. In Render, select that branch, keep root `server`, build `npm ci --omit=dev`, start `npm start`, health `/health`, Node 24 and one instance. Import the private ignored `server/.data/render-production.env`; never commit it. Preserve an already configured production `RATE_IDENTITY_SECRET` if one exists rather than rotating it unnecessarily.
3. The prepared settings permit public beta access and mark playtests unranked (`PLAYTEST_INVITE_ONLY=false`, `PLAYTEST_UNRANKED=true`). Finish old beta.1 matches before replacing that process: its in-memory matches cannot be recovered retrospectively. Future durable matches require the documented single-owner maintenance handoff.
4. Confirm the Render database is the intended production database and its migration inventory matches 001–006. The local read-only inventory does not prove an independently configured Render URL is identical. Do not reset data or auto-run migrations.
5. Deploy the backend, verify `/health` reports `0.3.0` and the release commit, then deploy/promote Vercel from that same commit. Keep the same-origin authentication/Socket.IO rewrites.
6. Run the read-only deployment check with expected version and commit. Exercise Google consent, an actual mail flow and headset quality across physical devices before broad playtest sign-off. Previously confirmed local Gmail receipt and synthetic audio cannot substitute for those hosted checks.

Google OAuth projects left in Testing can expire sender refresh tokens after seven days. Follow [Gmail setup](../gmail.md) for publishing/verification and account limits. Render Free cold starts and single-instance deployment interruption remain platform constraints. No destructive migration or production data reset is part of this update.
