# v0.3.0 headphone capture continuity

Date: 2026-11-13. Local update; not deployed. Version remains 0.3.0.

The user reported loud/continuous speech cutting out on localhost while the copied receive statistics showed no sampled loss, jitter or concealment. Those values do not prove microphone capture is healthy or identify the cause. Source inspection found echo cancellation enabled unconditionally, including headphone/same-computer testing.

Added **Audio setup** in Table Voice: Headphones (default, natural voice) requests echo cancellation, automatic gain and default noise suppression off; Speakers retains echo cancellation. Optional noise reduction remains off by default. Browser-local mode selection persists, and capture modes/noise processing can be changed only while muted. No constraints are reapplied during ordinary speech/meter updates. Speaker users must select Speakers to retain echo protection.

Added `voice-capture.js`, updated `VoiceChat.jsx` and lightweight voice styles. Report version `voice-transport-3` includes actual browser processing settings, microphone state, source mute count and sampled input level/clipping. Device/group identifiers and raw samples are excluded. Diagnostics reuse the existing meter and details timer; no new polling, server traffic, recording or external audio API. Missing values remain unreported rather than being presented as a healthy zero. Voice activity stays display-only.

Updated browser regression to send a continuous signal cycling through quiet, medium, loud and near-full-scale amplitudes. It checks actual headphone processing settings, continuity, echo-enabled speaker mode, mute/deafen, recovery and microphone release. Unit checks cover processing mode selection and privacy-preserving clipping measurement. Actual verification results are appended after completion.

Verification: four focused capture/transport unit tests passed; lint, production build and release checks passed. All four responsive layout browser checks passed. The final real two-browser voice regression passed with 120 playback samples and zero silent samples across the variable-amplitude source, with capture settings verified in Chrome and speaker echo protection verified after unmute. Its first run reached the successful 120-sample check but hit a new test race reading the reverse-direction capture before getUserMedia completed; moving that assertion after the existing capture-ready wait resolved the test without changing application behavior or weakening assertions. No live physical-headset success is claimed.

Scope/limits: this is a targeted capture-path change, not proof that browser echo cancellation caused this user's specific interruption. Synthetic sources cannot certify a real headset/driver/OS enhancement path. For one-computer normal/incognito tests, unmute only the sender and leave the receiver listen-only. Refresh both tabs and rejoin voice to use the new capture path. If sampled input clips, lower system/headset microphone gain; browser settings do not override all hardware processing.

Reference: [W3C capture constraint semantics](https://w3c.github.io/mediacapture-main/getusermedia#dom-mediatrackconstraintset-echocancellation). An unsupported constraint may be ignored; actual settings are included in the report for that reason. No transport bitrate, heartbeat, game rules, database schema or production configuration changed.
