# v0.3.0 update — Parties, personal records and mobile recovery

Date: 2026-11-15. Release branch: `release/v0.3.0-update`.

## Release contents

This release combines the previously isolated [party implementation](v0.3.0-parties.md) and [personal records/mobile hotfix](v0.3.0-records-mobile.md). Package versions remain 0.3.0; the Git revision identifies this update separately from the earlier `4139f1f` deployment.

- Persistent friend parties and optional voice that stays connected through matches and table changes.
- Personal games/wins include saved casual results, with competitive totals labeled separately.
- More tolerant heartbeats, authenticated foreground/network recovery, and bounded connection diagnostics in player reports.
- Existing authentication, accounts, game results, offline grace and AI allowances remain in place.

## Database handoff

Migrations 007 and 008 are additive. Migration 007 creates party tables. Migration 008 backfills casual-win counters from authoritative saved results; it does not import browser storage or promote casual results into ranked standings.

The production migrator must acquire the same exclusive ownership advisory lock as the game server before applying these migrations. It refuses to proceed while the old backend owns the database. Hold that lock throughout migration and verification, then release it before starting the new backend. Verify unchanged account counts, result counts and ranked totals, and compare every casual-win counter with saved casual victories.

Keep Render Auto-Deploy Off. Stop the old backend during a short maintenance handoff; do not terminate its database connection to force ownership. Confirm there are no active games immediately before handoff. Do not reset Neon, drop tables or overwrite production environment variables with local development settings.

Render settings: branch `release/v0.3.0-update`, root `server`, build `npm ci --omit=dev`, start `npm start`, Node 24. Existing Neon, Gmail and Cloudflare TURN configuration is reused. The new heartbeat settings have code defaults and require no environment edit.

For a manual Render rolling-deploy handoff, first deploy this release with the temporary Start Command `node scripts/maintenance.js`. This tiny process opens no database connection and accepts no game actions. Its `/health` returns HTTP 200 for platform checks but explicitly reports `ok:false, maintenance:true`; other routes return HTTP 503 with Retry-After. Once it is Live and the old ownership lock is released, apply and verify migrations. Restore Start Command `npm start` and manually deploy the same commit. Do not leave the service on the maintenance start command after migration.

Stage the frontend without promoting it. After the matching Render backend is healthy, promote that staged frontend and verify both `/health` and `/version.json` against the same Git revision. An old frontend remains compatible during the backend-first handoff; the new party interface requires the new backend.
