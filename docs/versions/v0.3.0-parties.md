# v0.3.0 — Persistent parties and party voice

Date: 2026-11-15. Prepared on `feature/party-voice`; this feature is not part of the currently deployed `4139f1f` runtime. Production migration and a coordinated deployment are required before the new Party control is live.

## Player experience

- Open **Party** in the visible side toolbar. Signed-in accounts can create a party, invite existing friends, accept/decline invitations and leave independently of their game table.
- A party holds up to ten accounts. Invitations are recipient-bound, friend-only and expire after ten minutes. Existing privacy preferences and block relationships are checked on invite/accept. An account belongs to at most one party.
- Membership and pending invitations survive refresh and backend restarts. Offline members keep their membership. Parties persist until their last member leaves; that deletes the empty group and its invitations. Account erasure removes membership. A departing leader transfers leadership to the oldest remaining member; the leader can remove members.
- Party voice continues through gameplay, results and leaving a table. Closing the drawer keeps the call running; the Party button shows **Mic on** or **Listening**. Voice activity badges reuse the existing local speech detector.
- Microphones remain opt-in. Refresh, disconnect, logout and leaving voice stop microphone capture. Returning restores membership, then requires Join Voice and Unmute again.
- Each socket uses one voice channel: joining table voice switches out of party voice and vice versa. Existing headphone/speaker capture modes, per-person volume, mute, deafen and TURN fallback are reused.
- Parties do not automatically move players into a new game or bypass room passwords/readiness. Existing friend table invitations and normal join controls continue to handle game entry.

## Implementation and security

`server/src/party.js` owns party mutations, bounded action-ID replay protection and sanitized snapshots. The socket's authenticated account owns its membership; a client cannot select an account or join by guessing a party ID. Only public Player Codes, names, avatar references and presence reach fellow members. Emails, internal account IDs, hands, game resume credentials, SDP and TURN provider secrets are not included in party snapshots.

Migration `007_parties.sql` adds `bx_parties`, `bx_party_members` and `bx_party_invites`, with ownership/expiry indexes and one-membership-per-account uniqueness. Mutations use the existing PostgreSQL transaction adapter and a transaction advisory lock. Friend/block validation uses the same stable user-row locks as social mutations. No authoritative membership change is installed or broadcast before its transaction commits.

Per-account and per-socket rate limits, payload bounds and bounded replay caches protect party events, including guest floods. Failed storage is reported without exposing SQL or credentials. Kicks and departures revoke cached voice authorization immediately after commit, before refreshing public state.

`server/src/voice.js` authorizes either a current game seat or party membership. Channels remain isolated and use fresh voice-session identifiers on a channel switch. Client cleanup includes its original voice ID, so an old table component cannot accidentally end a newer party call. Late mute requests are also checked against the current voice session.

`client/src/PartyPanel.jsx` remains mounted outside the conditional game screens. Hiding the drawer does not unmount the WebRTC controller. The theme-aware drawer includes keyboard focus trapping, a mobile layout, member list, invitations, host controls and a persistent mic status. No animation or speech meter is synchronized through Socket.IO.

No extra paid service, voice server, database polling or party countdown interval was introduced. PostgreSQL writes occur on party mutations. Connect/disconnect sends meaningful membership/presence updates; invite delivery does not rebroadcast an unchanged member snapshot. Existing WebRTC diagnostics run only while voice is joined. Ten simultaneous voice members use the existing mesh topology; a physical ten-device party is not claimed as qualified.

## Verification

The new real-browser scenario uses genuine account/friend transactions against an isolated PostgreSQL database. It creates two friends, sends and accepts a party invite, connects real browser audio, starts a game, ends it through a player's explicit departure, and verifies that both original audio elements/tracks remain alive through the winner screen and table exit. Refresh restores membership without reopening the microphone. Screenshots cover all three themes on mobile and the desktop result screen.

The default browser fixture uses pg-mem, whose social-card scalar subqueries do not reproduce PostgreSQL's result semantics. The full friend/audio test therefore runs explicitly through `npm run test:party` with the same disposable-database hostname guard as integration tests. It is a separate CI step against the workflow's PostgreSQL service; it is not mocked or silently treated as passed in the default browser command. Both browser modes use isolated ports 4020/5180 and local synthetic audio without paid TURN traffic.

## Deployment

No new environment variables are required; existing session, Neon and TURN settings are reused. Limits are centralized in `PARTY_RULES`: ten members, ten-minute invites, 512 cached action IDs, a 1024-byte request bound, a 20-event socket burst with two-per-second refill, and a 12-event account burst with one token per two seconds.

Migration 007 has been applied to the separate local **development** branch and the disposable test database. Production has not been migrated or deployed for this feature.

1. Review migration 007 and finish/recover any active matches using the existing maintenance procedure. Keep Render Auto-Deploy Off and one authoritative backend process.
2. Apply the additive migration only against the intended database. The local `.env.local` is now a separate **development** branch; running the default migration command locally does not migrate production. After explicit operator review, the private Render export can select the production target using `node --env-file=server/.data/render-production.env server/scripts/migrate-games.js`. This command has **not** been executed against production for this update.
3. Stop the old backend owner before starting the new release, then verify health and recovered matches. Publish the matching frontend afterward. Deploying the client alone does not enable the party API.
4. Test party invites, a complete match and voice with physical devices on separate networks. Synthetic audio and local tests do not establish physical headset or ten-person voice quality.

Existing accounts and historical game records are preserved. Voice audio itself is never recorded or stored, and live WebRTC sessions are not restored automatically after a server restart.
