# v0.3.0 — Deployment recovery and empty-database CI

Date: 2026-11-15.

## Two distinct causes

The Render release correctly checked out `4139f1f`, but startup retried `SERVER_ALREADY_RUNNING`. A local development backend was using the same production database. The single-owner advisory lock correctly prevented a second game controller from starting. The identified local Node watcher and its server child were stopped; no PostgreSQL session was forcibly terminated and no lock protection was removed. Render subsequently returned healthy `0.3.0:4139f1f0f91b467909a2d572d1605f3e3be70084`.

The GitHub Actions failure was separate: its fresh PostgreSQL service had no account schema. Real database tests previously passed on a Neon branch copied from an initialized database, which did not exercise that starting condition. The first game migration assumes `users` exists, so those CI tests failed with `42P01` before exercising game behavior.

## Fixes

- `server/test/prepare-postgres.cjs` runs the existing additive account/game migration entry point, only after loading the explicit isolated test database hostname guard.
- `npm run test:postgres` bootstraps the guarded database before running tests. Failed setup short-circuits the suite. No application startup migration setting or production SQL was changed.
- Local ignored `.env.local` now points to a separate Neon `development` branch, with pooled application and direct owner URLs. The private Render environment export retains the production URLs. Backend secrets in `server/.env` remain intact, but the root database override takes precedence.
- Render production should have Auto-Deploy Off for this single-owner architecture. Test/documentation-only changes do not require restarting the deployed application. Runtime deployments require a planned stop/start handoff; do not bypass the owner lock to obtain overlapping deployments.

## Verification and rollout

An entirely empty database was created inside the disposable audit branch, and its missing `users` and migration tables were checked before running setup. Setup successfully created the account schema and applied all six game migrations. All 30 PostgreSQL tests then passed, with zero skips or failures. The server suite passed again: 108 passed, six database-only cases skipped in that command. Lint and release checks passed.

Public production checks passed for both `https://bluffx.vercel.app` and `https://bluffx.onrender.com`, with matching `0.3.0` and revision `4139f1f0f91b467909a2d572d1605f3e3be70084`. Gmail is reported as the configured delivery provider. Vercel's promotion command reported that this build was already current; public version and proxy responses were checked directly rather than treating that message as proof. Browser checks on the public site passed at 390px and 1366px: guest menus and setup screens rendered without horizontal overflow, uncaught browser errors or requests to localhost. These hosted checks created no account, room, match or email. Real Google consent, mailbox receipt on Render and physical headset testing remain manual qualification steps.

The operator confirmed Render Auto-Deploy is Off before the CI-only patch was pushed. This patch changes test setup and documentation only; the deployed runtime remains the verified `4139f1f` build. GitHub Actions is rerun by the existing pull request when the patch is pushed; its result must be checked separately from the local results above.

No production data reset, destructive migration, force-unlock, PostgreSQL backend termination, or secret rotation was performed. Local backend development must continue to use the dedicated development branch; do not overwrite its URLs by pulling production environment variables into the local application configuration.
