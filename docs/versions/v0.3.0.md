## New gameplay and setup work

- `createDeck(deckCount)` produces shuffled cards with unique UUIDs, including duplicate-looking rank/suit cards. Recovery integrity validates exactly `52 × deckCount` unique IDs and exactly the configured number of each face.
- Ownership, selective challenges, penalties, final claims, discard retirement, turn indices and the existing maximum of four cards per play remain authoritative. No separate dual-deck engine was introduced.
- Classic, Party, Quick Match and Custom presets use validated configurations of the same engine. Classic uses four seats/one deck/30 seconds; Party suggests ten/two/20 seconds; Quick uses four/one/20 seconds. Supported timers remain 20/30/45/60 seconds. Explicit settings override recommendations.
- Optional room voice and AI playstyle are validated setup fields. Voice-disabled tables reject voice admission server-side.
- Host lobby settings can change capacity, deck count and timer; capacity cannot evict existing seats. Editing settings resets human readiness. A rematch clears completed-match AFK control; absent seats retain only their remaining grace budget rather than receiving renewed time.
- Rematch requests are visible to the table. The host reopens the existing room as a lobby; humans must ready up again. Legacy `restart_game` follows that same lobby transition; its explicit host click confirms only the host, while other humans must ready up again. The next start creates a fresh match/round identity and shuffled deck, preserving membership, social context and official profile statistics.
- Casual, Balanced and Aggressive bot profiles change bounded risk probabilities. They use the existing own-hand/public-claim selector and authoritative validation; no external AI, model or opponent-hand access was added. AI practice still supports the existing one-to-five bot range; the ten-seat expansion is for human multiplayer.

## Match insights, awards and results

New matches accumulate compact per-seat counters alongside authoritative state: cards played, claims made, challenges attempted/won/lost, unchallenged false claims and times caught bluffing. No duplicate full snapshot/event stream is introduced. Older recovered matches without counters do not receive manufactured historical insights.

Final results add server-derived duration, completed-round counter, deck mode, participant count, challenge outcomes and personal performance. Existing placements, forfeit and AI-assisted labels remain. Cosmetic awards use a minimum count of two and allow tied recipients: Master Bluffer, Human Lie Detector, Risk Taker and Unlucky Challenger. They never affect wins/rankings. The bluff metric is deliberately labeled **unchallenged bluffs**: it counts false claims that survived all passes, rather than claiming knowledge of every possible successful deception.

Aggregate summary metadata is stored once at match finalization. Private hands, account identifiers, participant names and raw resume credentials are not copied into the new history summary. The result screen uses the existing neon identity and winner presentation with an additional full-width insight/award section.

Ten-seat support also justified batching the existing result/statistics write loop: one transactional SQL statement inserts participant results and updates statistics only for newly inserted rows. The existing exactly-once match-finalization gate, constraints and rollback behavior remain. This bounds database round trips instead of adding two result/stat calls for every additional participant.

Sources: [match-insights](../../server/src/match-insights.js), [results UI](../../client/src/components.jsx), [game store](../../server/src/game-store.js).

## Social features

Verified accounts can open **Friends & Records** and obtain a random public identifier. Exact-identifier search returns public display fields, not email addresses or internal account IDs. Profiles are created lazily when social functionality is used.

- Send/accept/decline requests, remove friends, block/unblock accounts and list friends/requests.
- Privacy controls independently disable requests, invitations and recent-player discovery.
- The Privacy panel explains the new social records and controls; account-owned social/achievement rows are deleted with the account through foreign-key cascades.
- Transactional user-row locking serializes request/block races. Duplicate requests are rejected; declined requests have a 24-hour cooldown. Request/day and friend/inbox limits supplement the existing HTTP protections. Blocking retains cooldown history and removes invitations.
- Invite an accepted friend from an available lobby. Tokens are recipient-scoped, expire after ten minutes, and are checked again for friendship, blocking, capacity and lobby state. Duplicate active invitations are rejected and expired invitations are cleaned up.
- Opening an invitation only opens the normal join flow. It does not bypass passwords, host bans, capacity, account verification or playtest admissions.
- Copy room-code links use `?room=CODE`; the app opens the join form rather than silently creating a second seat.
- Recent players are optional, drawn from the latest 20 completed account matches, bounded to 20 results, exclude blocked/opted-out accounts and omit private match/room history.
- Targeted `social_updated` notifications refresh an open social panel after requests/invitations. There is no recurring social polling or database heartbeat. Global online/in-match presence disclosure is intentionally omitted.
- New social/history/achievement/season HTTP routes share a bounded signed-browser budget and generous coarse IP budget before authentication/database work. Rate-limit errors are structured and do not broadcast to a table.

Blocking controls social interactions; it is not automatic ejection of players already sharing a match. Host moderation remains the existing mechanism for removing someone from a table.

Sources: [social API](../../server/src/social.js), [Community UI](../../client/src/Community.jsx), [auth integration](../../server/src/auth.js).

## History, achievements and seasons

- Authenticated players can page through their own completed matches, 20 per page, with date, mode, placement, winner, privacy-filtered participant labels, verified/unranked status, forfeit/AI flags and recorded deck/player-count/duration metadata. Opponent names require discovery consent and no mutual block; otherwise the label is Private player. Unknown legacy metadata is shown as unrecorded, not guessed. Other accounts' histories are not accessible through a supplied user ID.
- Cosmetic achievements are unlocked only inside legitimate result finalization, using a unique `(user_id, achievement)` key. Clients cannot submit unlocks. Eligible ranked human results can unlock first/five/ten wins, ten matches, first unchallenged bluff, first/five correct challenges, a perfect challenge match with at least three attempts, Party Player and Double Trouble. The cumulative challenge threshold excludes practice/AI/forfeit counters. Achievement processing batches eligible statistics and inserts into at most two additional SQL driver calls for the match, rather than querying/inserting separately for each unlock.
- Unranked playtests, practice, AI-assisted participants and forfeits do not unlock these ranked achievements. Existing pair-cap eligibility is preserved. Unlocks are listed once in the profile panel; no duplicate toast stream is generated.
- Existing all-time rankings remain. A current-season view uses server-defined UTC calendar quarters, preserves historical results, excludes unranked matches and uses indexed authoritative timestamps/results. The endpoint supports a friend filter and win-rate ordering with a ten-match minimum; the initial UI exposes the current-season victories view.
- No XP, currency, odds advantage or client-assigned ranking points were introduced.

Sources: [history/season endpoints](../../server/src/history.js), [achievement rules](../../server/src/progression.js).

## Voice decision and measurements

Mesh/TURN behavior was preserved, not rebuilt. SFU routing and SFU session authorization remain absent because activating that optional architecture would require both implementation and cost approval. Current provider documentation includes overage pricing, and a provider-enforced zero-spend cap was not verified. See the [SFU assessment](../voice-sfu-assessment.md), including source links and existing TURN overage considerations.

A local opt-in experiment established ten voice participants with nine connections each. One speaker sent audio to nine receivers, with roughly 167 kbps aggregate sender RTP, zero sampled packet loss and 1 ms maximum reported jitter. Host-page heap was about 11.6 MiB. The separate headless lobby animation sample was 144.7 frames/second; it is not gameplay FPS. Raw [voice measurements](../performance/v3-ten-voice.json) state their limitations. No cloud relay/SFU traffic was generated by this experiment.

## Network, preferences and accessibility

The existing reconnect/loading flow remains authoritative and clears stale queued actions. The interface now reports **Slow action responses** from real action acknowledgements over 1.5 seconds, rather than issuing extra probes or claiming that acknowledgement time equals network-only ping.

Preferences centralizes a browser-local reduced-motion override, alongside existing in-table voice controls. CSS also honors the operating system's reduced-motion preference. Focus outlines, native labeled controls, touch-sized setup segments, readable large-room labels and responsive invitation/readiness controls retain the game's visual identity. Optional controls with no working effect were not added.

## Performance evidence

The local 20-room/360-action/120-round load sample used a 128 MiB heap cap and the in-memory persistence test double. Average acknowledgement was 13.05 ms; p95 16.97 ms. Measured workload CPU was 437 ms, RSS 110.7 MiB, used heap 29.5 MiB and event-loop p95 about 32 ms. There were 360 durable-test-double commits, 960 application notifications and 981,206 payload bytes. The two-second idle window produced zero commits, receipt lookups or notifications. Raw result: [v3-local.json](../performance/v3-local.json).

An earlier run overlapping the browser voice experiment showed higher local latency and was not used as a like-for-like improvement claim. RSS/CPU include the local load clients as well as the server. These are synthetic host/process observations, not Render capacity or real Neon commit latency. Historical beta benchmarks remain historical.

Three explicit read-only requests to the live Render `/health` endpoint measured 280, 86 and 92 ms on 2026-11-13; all returned HTTP 200 and beta.1. These measure HTTP response time only, not v0.3.0 game actions, database latency or a proven cold start. The repeatable [network sampling script](../../server/scripts/measure-network.js) requires `--allow-live` for remote sampling and never runs continuously.

## Deliberately excluded or still pending

- SFU activation and SFU session authorization: blocked by the zero-spend gate, not described as implemented.
- Public room discovery, global friend presence, XP/levels, heuristic punishments, full private replay and comeback awards: optional scope omitted to avoid activity leaks, farming incentives and unreliable metrics.
- Extra guided-practice scenarios were not added; the existing replayable eight-step tutorial already teaches the core claims/challenges/final-claim flow and remains unchanged.
- A new push-to-talk/device-selection system, Bluetooth recovery and game-music controls were not added. Existing working voice controls remain.
- Season friend/rate filters are backend-supported but are not yet exposed as full UI filters. History omits internal identifiers/private-room details, anonymizes non-consenting/blocked participants and does not offer a full recap/replay.
- Real mobile/headset/different-network voice, ten simultaneous speakers, Render CPU/memory visibility, v0.3.0 cloud gameplay/FPS and production cold-start testing remain physical/staging playtests. Headless lobby measurements do not substitute for them.
- The new hosted CI run, production Google/Resend smoke tests and backup/restore drill remain deployment checks. No paid service, cloud resource or overage option was provisioned.
