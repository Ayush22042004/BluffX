# v0.3.0 — Gmail authorization diagnosis

2026-11-27. The user reported both account emails and report notifications failing in production. The configured local Gmail sender was tested with a token-refresh request only: HTTP 400, `invalid_grant`. No email was sent and no production database or account was modified. Production environment credentials have not been inspected, so equivalence with the local token is not assumed.

Added `npm run check:email -- --provider gmail --check-auth` to verify authorization without sending email. The Gmail adapter reports only allowlisted OAuth failure reasons, never raw descriptions or token responses. A successful check returns only `{ authorized: true }`. There is no periodic token refresh or database polling.

Repair requires checking the Google OAuth sender project's publishing status, completing fresh sender authorization and replacing the backend's private `GMAIL_REFRESH_TOKEN`. External Testing-mode Gmail refresh tokens expire after seven days; other revocation causes are possible. Publishing a project does not restore an already-invalid token. Follow [the Gmail setup guide](../gmail.md) and applicable Google verification requirements. Delivery is not fixed or certified until the replacement credentials are checked in the target environment and inbox receipt is verified.

Modified files: `server/src/gmail-api.js`, `server/src/mailer.js`, `server/scripts/check-email.js`, `server/test/gmail-api.test.js`, `docs/gmail.md`, root README and version index/this record. No migrations, paid services or environment variable additions.

Verification: Gmail adapter tests 3 passed; lint passed. Live authorization-only check correctly failed with HTTP 400 / `invalid_grant`. The failure remains a configuration/authorization dependency, not a passing delivery test.
