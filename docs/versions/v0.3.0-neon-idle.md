# v0.3.0 — Neon idle efficiency

Date: 2026-11-26. Backend implementation; not deployed by this update. No schema migration, account conversion, additional dependency or paid service is required.

## Root causes and audit

The authentication cleanup interval issued SQL every 60 seconds even with no players: expired sessions, tokens, erasure queue, reports and avatars, plus expired invites in the full server. A standalone deterministic baseline measured five queries in one idle minute. The separate hourly room-retention interval also woke PostgreSQL unnecessarily.

The game server held a direct session advisory lock. Neon may close idle connections when suspending; the original owner-loss supervisor would immediately reconnect, query and recover, waking storage again. An idle TCP connection or TCP keepalive is not itself a SQL query; removing pooling alone would not fix the cleanup traffic.

The existing `/health` handler did not query PostgreSQL, but treated temporary storage failure as failed process liveness. It now reports process liveness independently. `/ready` provides cached readiness without querying storage. Neither endpoint proves database availability by probing it.

Frontend inspection found no recurring authentication, history or leaderboard database polling. Startup retries are bounded; view changes and authoritative update events request fresh information. Browser countdowns and voice statistics are local. Socket.IO heartbeat traffic does not access PostgreSQL. Session validation remains immediate on authenticated gameplay actions, now using one joined query instead of two, without caching revocations.

Runtime `SELECT 1` keepalive queries were not found. `EXISTS(SELECT 1 ...)` clauses implement actual authorization/business checks. The standalone Neon diagnostic script makes an explicit one-off probe. Transactions release clients in `finally`; rollback errors no longer mask the original failure. A read-only production long-running-query check returned no rows. Query history inspection was unavailable because `pg_stat_statements` is not installed; this update does not install it.

## Implementation

- Idle connection pools have minimum zero, a 10-second idle timeout, and existing small maximums (game four, auth two). There is no periodic database ping.
- One managed 30-second inactivity deadline releases the game ownership session only when no active match, pending mutation, disconnect or reload requires it. Lobby sockets can remain connected. Active gameplay, result countdowns and provisional outcomes retain ownership and existing timers.
- The next database operation reacquires the advisory lock and increments the existing fencing epoch. Concurrent requests share one wake operation. If no intervening owner existed, memory stays authoritative and unchanged lobbies are not persisted again. If another owner existed, durable rooms and authorized connected seats are restored before requests continue. Failed wakes return a safe 503 and do not loop autonomously.
- Startup still performs mandatory schema validation and active-match recovery once. Recovery is not postponed until the first player; committed expired deadlines must resolve correctly. Normal post-start database work is demand-driven.
- Retention runs at most hourly after successful database activity. There is no retention interval. Logical session/token expiry is still checked on every use; physical deletion can wait until activity resumes. Explicit account erasure remains immediate.
- Duplicate actions retain the existing receipt/idempotency handling before storage access. Actual moves still require successful durable commits before acknowledgement/broadcast. No gameplay transaction is blindly retried.
- Pending report-email retries and real game deadlines remain intentional scheduled work. An empty report queue does not poll. An idle room's actual expiry may cause a bounded write; an active match or due mail delivery legitimately wakes storage.
- Diagnostics add in-memory auth SQL counts, pool counts, storage wake/failure counts and idle status. Health never queries these from Neon. `storage: idle` means this process released ownership, not a live cloud-control-plane lookup.

## Configuration

| Variable | Default | Purpose |
| --- | --- | --- |
| `GAME_DB_IDLE_MS` | `30000` | Application ownership release after safe inactivity; range 1000–120000 ms |
| `DB_POOL_IDLE_MS` | `10000` | Idle pooled client release; range 1000–30000 ms |
| `DB_MAINTENANCE_MS` | `3600000` | Minimum interval between demand-triggered retention; range 60000–86400000 ms |

No new credentials are needed. Production compute was configured at 0.25 CU with suspend timeout `0` (plan default), not disabled. Neon's free-plan default is five minutes without active queries. App connection release does not change that server-side timeout. See [Neon scale to zero](https://neon.com/docs/introduction/scale-to-zero). Other applications, SQL editors, monitoring queries or old BluffX processes using the same branch can still prevent suspension.

## Measured verification

An isolated, schema-only Neon branch with automatic expiry was used; production data was not migrated, reset or written. The real idle probe used the default application/pool idle settings, issued 12 liveness requests over 360,181 ms and measured:

| Measurement | Result |
| --- | --- |
| Background auth queries in deterministic one-minute baseline | Before 5; after 0 |
| Six-minute idle runtime game/auth SQL delta | 0 / 0 |
| Remaining game/auth pooled connections | 0 / 0 |
| Ownership session released | Yes |
| Autonomous recovery restart | No |
| Neon control-plane compute state before cold request | `idle` |
| First real leaderboard request after suspension | HTTP 200 in 4191 ms |
| Advisory ownership reacquired | Yes |

This is an observed cold-start sample, not a latency guarantee or monthly CU savings projection. The six-minute probe preceded the final same-owner fast path; its zero-idle-SQL behavior is unchanged. The final fast path is separately checked by the PostgreSQL integration test.

New tests cover idle/no-poll behavior, maintenance throttling, single-flight cold recovery, safe failure, zero-SQL health requests, zero pooled clients, unchanged lobby versions on a cold read, ownership contention, authenticated stats, fresh transport seat recovery and legal gameplay after wake. Existing restart tests now clean up only their own saved rooms instead of leaving active fixtures behind.

## Safe rollout and limitations

Keep Render on a single backend instance, Auto-Deploy Off, root `server`, build `npm ci --omit=dev`, start `npm start`, health path `/health`. Deploy the verified main commit manually. Preserve all existing database/auth/mail/voice environment values. New settings are optional and default automatically. No migration or Vercel frontend deployment is required.

Use the existing maintenance handoff if the previous process holds the ownership lock; do not clear locks or terminate arbitrary database sessions. After rollout, check `/health` and `/ready`, sign in, resume a saved table, complete a match and inspect history. Then leave the application idle with no active matches, due mail or SQL consoles and verify the Neon dashboard shows suspension after its inactivity window. Do not add a database-querying health monitor.

Active matches intentionally prevent this application's ownership release. First use after suspension may take several seconds; failures remain recoverable and mutations never fall back to memory-only commits. This update does not claim production savings until the Render process runs the new code and actual production idle behavior is observed.
